# 16 对端与网络来话 APP 监听

开发版本：固件 r11-85，APP 1.2.15-heimao（versionCode 27）。未发布，实板验收待进行。
保留 r11-84 的发射后接收抑制功能。

## 公网直连 16 个对端

每台手台最多保存 16 个公网直连对端，不含本机；额外的内部自测槽不开放给用户。
单中心 hub 可以配置最多 16 台成员。该数量是本机对端表容量，不是任意拓扑的全网规模保证。
当前不提供 32 个对端或无限连接。

- 配置空对端不预留音频缓冲。首次收到音频才分配 PSRAM 缓冲和序号/有效位；解码器在首次播放时创建。
- 每个已分配音频槽使用 `128 × (80 + 2 + 1) = 10624` 字节，不含解码器和设备元数据。
  删除、远端 BYE、引擎停止会释放音频资源，重新使用时再创建。
- 满表添加新对端返回明确错误，不替换旧条目；已有地址的更新仍允许。满表时也拒绝未知发送者占用旧槽。
- `links n/16` 与网页/APP 的容量来自固件；`peer_count` 是保存的条目数，`links` 是已连通数。
- `/api/status` 为完整 16 行预留 5120 字节，整个响应在 PSRAM 分配 12288 字节；非必要日志先让出空间。
  APP/网页发现实际返回行数少于 `peer_count` 时会明确提示，不把缺失行当成没有对端。
- `np2p.jbuf_bytes` 报告已分配的音频缓存，`drop_full` 报告满表拒绝未知发送者次数。
  `save_pending=true` 表示 NVS 保存失败、等待后续 HTTP 状态读取重试。

配置存储改用 `orl/np_peer3`，带版本、条目数、条目宽度与 IPv4/IPv6 地址。
首次启动读取 v3；不存在或无效时尝试原 `np_peer2` / `np_peers`，保留原四个条目，
并在安全的 HTTP 任务上保存新格式。同时恢复 hub 和 STUN 设置。
旧键保持原样，供有意回退旧固件时使用；**新版本之后的条目编辑不会同步进旧的四槽键**。

扩容不增加多人混音或抢话仲裁。仍播放最近活跃发送者；实际 Wi-Fi、CPU、丢包和延迟
需要多设备实测，不能仅凭表容量或 PSRAM 剩余量认定稳定支持人数。

## 网络来话同时送往射频和 APP

```text
远端 P2P/MQTT 音频解码
    ├─ 手机/网页收听（原始解码 PCM）
    └─ 既有桥接处理 → 本机射频 → 模拟中继
```

APP 的网络监听分支位于本机射频 BGTX、MIC EQ、喇叭音量等处理之前，
调整本机射频重发音量不会改变这一份手机音频。不额外生成尾音，不改现有射频路径。

接收环统一区分 RF 与 network 来源：

- 有网络音频时优先送网络；短播放间隙保持 250 ms 音源优先权，音频本身立即入环，不为此延迟播放。
- 射频静噪关闭、桥接注入和 RF 接收保护只关闭 RF 来源，不能清掉网络音频。
- 本机 APP PTT 上行开始时清空接收环并静音，直到本轮释放和尾音完成才恢复，避免自身回声。
- B 代远端进行射频发射时属于 NETWORK 来源，不触发本机 APP 上行静音。
- 切模式、关闭会话、重连以及切换音源会清理旧音频；旧网络引擎的推送不能写入其他模式。
- 网络音频只分给监听和原射频路径，不经 RF→网络入口再发回网络。

沿用已有 16 kHz PCM16 WebSocket/HTTP 协议，旧 APP 也能收听这条新增分流。
同一手台仍维持原来的单个活动 SDR 收听会话限制，本功能不新增多手机同时收听。
`sdr.rx_source`、`rf_samples`、`network_samples` 提供音源与送入监听环的样本计数。

## 验证范围

主机测试使用真实生产函数：旧格式迁移、16 条目、满表拒绝、1000 次删除/添加/收音分配回收，
模拟保活/过期/重连、hub 转发到其余 15 个成员、完整 IPv6 状态序列化。
两套网络引擎的 monitor/direct 播放分支均验证 APP 原始 PCM 分流、RF 关闭交错、
本机 APP 发话静音；另测来源切换、模式失配和有界接收环。
这些是主机替身测试，不是 16 台真实手台或真实 Wi-Fi 的压力测试。

实板验收重点：A、B 各连接模拟中继，两侧 APP 开启收听。分别从 A APP、B APP、
A 模拟端、B 模拟端发话，确认应到达的模拟端和 APP 都能听见，且不自回声、
不重复尾音、不循环回传。P2P/MQTT、桥接开关、接收保护、快速连按、断网重连各走一遍。
